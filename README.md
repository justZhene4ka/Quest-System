# 🗺️ Quest System

## 📌 Описание проекта
**Quest System** — это концепция модульной платформы для создания и проведения интерактивных гибридных квестов (online + offline). Система геймифицирует процесс решения задач, объединяя нарративный дизайн, шифрование, механику "услуг" и создание физических артефактов в реальном мире.

Данный репозиторий представляет собой **аналитическую спецификацию (SRS/PRD)**. Он демонстрирует навыки системного анализа: от сбора бизнес-требований и моделирования процессов до проектирования архитектуры, структуры данных и API-контрактов. Физическая разработка бэкенда не производилась.

## 🎯 Видение и бизнес-ценность
Предоставить универсальный инструмент для усиления вовлеченности через геймификацию. 
**Целевые сегменты:**
- **B2C:** Пары (романтические квесты, поиск подарков), компании друзей, любители текстовых RPG.
- **B2B:** Корпоративные тимбилдинги, онбординг новых сотрудников, геймификация карьерного роста.
- **Vision (Будущее):** Подключение AI-агента для автоматической генерации сценариев на основе контекста, предоставленного заказчиком.

## 👥 Акторы и Роли
1. **Игрок (Player):** Проходит этапы квеста, выполняет оффлайн-действия, загружает медиа-подтверждения, инициирует "сеанс связи" (авторизация).
2. **NPC (Автоматизированный агент):** 
   - Ведет диалог в заданном Tone of Voice.
   - Алгоритмически валидирует ответы и выдает подсказки строго после выполнения "услуг".
   - При получении нестандартного запроса инициирует эскалацию на Админа (паттерн *Human-in-the-loop*).
3. **Админ / Гейм-мастер (Game Master):** 
   - *MVP:* Взаимодействует через Telegram (пересылка сообщений), вручную валидирует сложные артефакты и обучает NPC новым ответам на edge-cases.
   - *Target Architecture:* Использует выделенную Helpdesk-панель для управления активными сессиями, сценариями и аналитикой.

## ⚙️ Ключевые системные механики
- **Инициализация сеанса (Auth):** Уникальный механизм входа в квест (например, фото удостоверения, кодовое слово или внешняя SSO), открывающий доступ к цепочке заданий.
- **Гибридные задачи:** Сочетание цифровых шифров (акростих, шифр румбов) с физическими действиями (вязка узлов, поиск предметов в комнате).
- **Экономика "Услуга за подсказку":** Механизм снижения фрустрации. Подсказка не дается бесплатно, а "покупается" за выполнение микро-задания (голосовое, фото, текстовый отчет), что сохраняет игровой тон.
- **Разделение контента и логики (Decoupling):** Сценарии, диалоги и правила хранятся отдельно от кода бота (JSON/YAML/DB), что позволяет разворачивать новые квесты без изменения программного кода.

## 🛠️ Рекомендуемый стек технологий (Архитектурный концепт)
*Примечание: Проект является аналитическим концептом. Ниже представлена целевая архитектура для передачи в разработку.*

- **Канал взаимодействия (Frontend):** Telegram Bot API (MVP), Web-интерфейс (Target).
- **Backend:** Python (FastAPI / Aiogram) или Node.js для асинхронной обработки событий.
- **База данных:** PostgreSQL (хранение прогресса, пользователей, конфигураций квестов).
- **Хранилище медиа:** S3-compatible storage (MinIO, Yandex Object Storage) для фото/аудио игроков.
- **Политика конфиденциальности (NFR):** Конфигурируемый клиентом выбор: 
  1. *Эфемерное хранение:* Данные удаляются сразу после завершения квеста (Default, Privacy-first).
  2. *Передача прав:* Архив медиа выгружается на диск заказчика по окончании.
- **Инструменты аналитика:** Mermaid.js / Draw.io (диаграммы), Swagger/OpenAPI (контракты).

## 🚀 Гипотетический процесс развертывания (Deployment Concept)
*Описание того, как данная спецификация превращается в работающий продукт:*
1. **Infrastructure:** Инженер разворачивает PostgreSQL и S3-хранилище согласно [ER-диаграмме](./docs/erd.md).
2. **Backend:** Разработчик реализует эндпоинты по [API Specification](./docs/api.md) и настраивает машину состояний (State Machine) для диалогов NPC.
3. **Content:** Гейм-дизайнер загружает JSON-файлы сценария в систему, не затрагивая код.
4. **Launch:** Бот подключается к Telegram API, проходит тестовый сценарий и открывается для игроков.
